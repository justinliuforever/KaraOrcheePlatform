## 1. WHAT WAS LYING

### The one that misdirected every session: `CLAUDE.md` Project References

Loaded into every session in this repo, it named two documents as the authorities:

> `notes/architecture.md` — DB schema, API routes, auth system, activation codes, newsletter system
> `notes/azure-infra.md` — Azure tenants, subscriptions, resources, App Registration, az CLI commands

**Truth:** `architecture.md` (last touched 2026-02-28) describes the *old web system* — Vite dev server on 5173, backend on 5555, admin on 5174, MongoDB collection `music_tracks`, `KARA-XXXX-XXXX` activation codes, email subscriptions. Its content is accurate; every claim in it was verified. What was false was calling it "the DB schema, API routes, auth system" with no scope line, in a repo whose sibling is the Notes platform. Now scoped and retitled; kept, because it is the only description of a system that is still running (`app-music-backend` = Running).

`azure-infra.md` was cited as required reading "before any `az` CLI work" and contained **none** of `rg-karaorchee-app-dev` — not `ca-app-api-dev`, `ca-notes-worker-dev`, `stkaraoappdev`, or `pg-karaorchee-app-dev`. All 11 resources the platform runs on were absent, as were `acrkaraorchee` (which *both* systems build into), `email-karaorchee`, `swa-karaorchee` (holds karaorchee.com), `ca-cv-backend`, `rg-piano-amt`, `rg-dev-vm`. A session obeying this file would have operated on the wrong resource group. Rewritten as three labelled inventories with live revision numbers, ~30 resources, detail delegated to `platform.md`.

### Two more lines in the same file, equally load-bearing

> "Entra External ID (CIAM) tokens: use `idToken` not `accessToken`"

**False for everything we now build.** `App/Platform/AccountService.swift` uses `accessToken` exclusively — `idToken` appears nowhere in `App/` — and `api/src/auth.ts` validates by audience. `platform.md` calls doing what CLAUDE.md instructed "the legacy trap". The rule was true only of the old web app (`AzureAuthContext.jsx:44`). Rewritten as a two-system contrast, not deleted.

> "Always use API keys / connection strings, never credential-based auth"

**Has a shipped counter-example.** `api/src/opslogs.ts` uses `DefaultAzureCredential` because Log Analytics accepts Entra auth only. Absolute phrasing invites a future session to "fix" working code. Now stated as the one exception.

### 1b. Found while verifying — the code is wrong, not the doc

Three defects surfaced by checking docs against code. **No code was touched.**

Two accounts on one device silently steal each other's token row.
2. **Worker failures cannot reach the Ops Errors page.** `api/src/opslogs.ts:110,123-126` maps `kind == "raw"` to `warn`.

Deploying flips the founder-gated retention rules **on** and **drops** the live one. Also `main.bicep:250` names only the pieces worker in its drift warning; `ca-notes-worker-<env>` is equally CLI-managed. `backupRetentionDays: 7` vs live 35.
